# VentoOS 架构师审查

- 角色目标：评估当前系统在职责划分、能力边界、扩展路径和系统一致性上的问题。
- 审查结论：当前架构具备平台雏形，但“产品外壳先行、业务能力补齐滞后”的特征明显，若不尽快做边界收束，后续会演变为表层完整、底层分叉的系统。

## 一、架构层判断

- 优点：
  - web 与 native 的层次分离总体清晰。
  - 已出现平台化趋势，如统一任务、统一窗口、统一代理会话模型。
  - Rust workspace 划分清楚，说明模块化意识存在。
- 问题：
  - UI 先行暴露大量能力，但后端和真实执行链路没有同步收口。
  - “调试能力”“产品能力”“底层设施能力”在若干模块中混在一起。
  - 某些核心边界尚未真正落地，例如事件总线、订阅系统、插件消息桥接。

| 等级 | 问题 | 证据 | 架构影响 |

## 三、架构性缺口

### 1. 平台事件总线没有完成“可扩展”这一步

- 协议层已经定义了 Subscribe、Unsubscribe、AppMessage。
- 服务器处理层没有兑现这些协议语义。
- 结果是协议设计比实现超前，系统处于“接口存在但平台能力未兑现”的状态。

### 2. 调试平台与业务平台界限模糊

- API Client 的代理能力本质上是一个网络调试工作台。
- 这类能力在架构上通常需要独立权限、独立审计甚至独立部署。
- 当前它已经进入统一产品路由与前端应用集合，会放大治理成本。

### 3. 发布链路与运行链路还未统一

- File Provider 缺包时自动下载补齐，说明运行时在补发布时的缺口。
- 这会导致“代码仓库版本”“实际安装版本”“远端下载版本”三者可能不一致。

## 四、建议的架构动作

1. 把事件总线建设为明确的中心能力，至少先完成订阅管理、频道隔离和插件消息转发。
2. 将 API Client 代理能力定义为受控工作台，而不是默认产品基础能力。
3. 把 File Provider 安装、版本、签名与升级并入统一发布流程，避免运行时兜底下载。
4. 对所有“接口已存在但语义仍为 stub”的模块建立一张平台债务表，禁止继续无标识暴露到 UI。
