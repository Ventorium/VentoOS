# VentoOS 测试质量工程师审查

- 角色目标：识别当前测试体系是否能有效阻止“假实现上线”和“接口存在但行为错误”的问题。
- 审查结论：项目并非没有测试，但测试结构偏前端组件和 Mock 场景，对高风险原生模块与真实集成链路的保护不足。

## 一、当前测试面概览

- web/package.json 已配置 Vitest、Testing Library、jsdom。
- web 内已有窗口、Dock、通知中心、设置等前端测试。
- native 采用 Cargo workspace，部分类库含测试。
- 但关键模块的测试分布不均衡。

## 二、主要问题

| 等级 | 问题 | 证据 | 影响 |
|------|------|------|------|
| P1 | 前端关键测试大量依赖 mock API，难以发现真实后端缺口 | web/src/kernel/__tests__/windowStore.test.ts:1-50；web/src/shell/__tests__/Window.test.tsx；web/src/shell/__tests__/NotificationCenter.test.tsx | 组件测试会通过，但接口语义虚假时仍无法预警 |
| P1 | native/crates/ventoos-api-client 缺少独立 tests 目录 | native/crates/ventoos-api-client/tests 不存在 | 代理、协议运行时等高风险逻辑缺少针对性验证 |
| P1 | native/crates/ventoos-mount 缺少独立 tests 目录 | native/crates/ventoos-mount/tests 不存在 | File Provider 安装、下载、解压、挂载链路缺少自动回归 |
| P1 | native/fileprovider 未见测试目录 | native/fileprovider/Sources/*.swift | token 传递、URL 拼接、错误恢复等行为没有自动验证 |

## 三、核心判断

### 1. Mock 保护了渲染，却没有保护行为真实性

- windowStore、Window、NotificationCenter 等测试都通过 mock API 固定返回值。
- 这类测试适合验证渲染与状态变换，但不适合发现“后端路由虽然存在，实际逻辑仍是 stub”的问题。

### 2. 高风险模块缺少模块级或集成级测试

- API Client 代理、协议运行时、Mount、Swift File Provider 都是系统边界模块。
- 这些模块一旦出错，影响的是整个系统连通性、安全性或安装链路。
- 当前缺口说明测试资源更多投在前端交互层，而不是系统边界层。

### 3. 缺少“禁止假实现进入可见路径”的验收测试

- 例如 SSH test_server 当前固定成功，这类问题若有最小集成测试，本应很容易暴露。
- 当前测试结构没有形成这种闸门。

## 四、建议

1. 为 native/crates/ventoos-api-client 增加代理目标限制、协议会话和审计行为测试。
2. 为 native/crates/ventoos-mount 增加下载校验、解压失败、包缺失与回滚测试。
3. 为 native/fileprovider 增加最小 Swift 单元测试，重点覆盖 token 处理和 URL 生成。
4. 为 SSH、WebSocket、Kubernetes 关键路径增加“真实语义”集成测试，而不仅是 UI 渲染测试。
5. 增加一类发布前验收：凡标记为“连接测试”“保存成功”“删除成功”的动作，都必须有端到端验证。
