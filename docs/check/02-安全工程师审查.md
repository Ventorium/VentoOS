# VentoOS 安全工程师审查

- 角色目标：识别当前实现中已经形成实际风险暴露面的认证、代理、凭证、下载与默认安全策略问题。
- 审查结论：当前最值得优先处理的不是传统内存安全问题，而是令牌泄露面、通用代理边界过宽，以及部分设计文档未坚持 secure by default。

## 一、重点风险结论

| 等级 | 风险 | 证据 | 说明 |
|------|------|------|------|
| P0 | 令牌通过 URL 查询参数传递，且被日志打印 | native/fileprovider/Sources/VentoAPIClient.swift:101-126 | token 进入 URL 后会落入日志、代理、系统抓包与历史记录 |

## 二、详细分析

### 1. File Provider 的 token 处理存在直接泄露面

- listDir、stat、readFile 会把 authToken 拼接到 query string。
- 同时代码使用 NSLog 输出 apiPath。
- 这意味着 token 不只是“传输在 URL 中”，而是已进入本地日志文本。
- 该问题优先级应高于一般性的“Header 与 Query 参数风格不一致”，因为它已经构成实际泄露路径。

###+ 建议

- 一律改为 Authorization Header 或等价的安全 header 方案。
- 彻底移除日志中的完整请求路径，至少对 path 与 token 做脱敏。

### 2. API Client 的通用代理边界过宽

- execute_proxy 允许任意 method、url、header、body、timeout、redirect 策略。
- 路由层直接将该能力暴露为 proxy_rest。
- 前端也提供完整调用接口，说明这不是保留中的内部 helper，而是产品能力的一部分。
- 在局部代码中未看到目标地址 allowlist、协议限制、私网网段限制、审计策略或按连接对象授权的约束。

###+ 风险说明

- 如果缺乏全局中间件兜底，该能力可能被用作 SSRF、内网扫描、凭证转发或代理下载。
- 即使存在登录态保护，这种通用代理能力仍应限制目标范围，否则等于把服务端变成网络跳板。

###+ 建议

- 增加显式 allowlist、按 workspace/connection 维度授权、私网地址策略与审计日志。
- 将“调试型代理能力”与“生产型业务能力”拆分部署或按角色隐藏。

### 3. 远程下载应用包但未校验完整性

- fileprovider_impl.rs 中若本地无包，会从 VENTOFS_DOWNLOAD_URL 下载 zip，再调用 unzip 解压。
- 当前实现没有签名验证、checksum 校验或版本信任链。
- 这不是命令注入问题，因为这里使用的是参数化 Command::new，而不是 shell 拼接。
- 真实风险在于供应链和完整性校验不足。

### 4. 设计文档没有坚持安全默认值

- docs/requirements/05-vfs/webdav-需求.md 明确展示 user:pass@host 形式的 URL。
- 文档同时允许 webdav:// 与 HTTP Basic Auth。
- 这会把不安全习惯直接固化进实现与测试样例中。

## 三、优先整改建议

1. 立即修复 File Provider token 传递与日志打印问题。
2. 对 API Client 的 REST/WebSocket/MQTT 代理增加目标限制和权限模型。
3. 为远程下载包补充 checksum 或签名校验。
4. 修改 WebDAV 设计文档，默认仅允许 HTTPS，禁止在 URL 中携带凭证。
