# VentoOS 系统设计开发工程师审查

- 角色目标：从功能实现和用户路径视角，确认哪些能力已经闭环，哪些能力仍停留在展示层或假实现阶段。
- 审查结论：系统壳层能力强于业务能力，多个已暴露到界面的操作并未形成真正闭环。

## 一、总体判断

- Web Shell、窗口系统、主题和部分基础能力完成度较高。
- 数据库、Kubernetes、SSH、通用 WebSocket 插件消息等关键能力仍存在明显缺口。
- 问题的严重性不在于存在 TODO，而在于部分 TODO 位于用户可触发的操作路径中。

| 等级 | 问题 | 证据 | 影响 |
|------|------|------|------|
| P1 | SQL 编辑器“保存查询”无实际行为 | web/src/apps/database/components/SqlEditor.tsx:114 | 用户可见操作无效果，无法形成查询管理能力 |

## 三、问题分析

### 1. 可见操作未闭环

- SqlEditor 的 handleSave 只有 TODO，没有调用任何存储或后端接口。
- TableDesigner 的 handleSave 仅通过 500ms 延时模拟保存，代码本身已明确 TODO。
- 这类问题不属于“后台未准备好”，而属于前端已经暴露行为但未做能力门禁。

### 2. 列表操作能力不完整

- Kubernetes ResourceToolbar 已向用户暴露 selectedCount 与删除入口。
- onDeleteSelected 仍为空实现，说明列表选择与批量操作链路只完成了 UI 前半段。

### 3. 事件总线只完成了最窄子集

- native/crates/ventoos-server/src/websocket.rs 当前只把 task event 转发给客户端。
- Subscribe、Unsubscribe、AppMessage 都只有日志和 TODO。
- 这与 WebOS/Workbench 风格产品“多域事件协同”的目标不匹配。

### 4. 健康检查/连接测试存在假阳性

- SSH test_server 固定返回 success=true、latency=35ms。
- 这会直接破坏用户对“连接测试”的信任，属于高优先级功能质量问题。

## 四、未完成项清单

- 数据库查询保存
- 数据库表结构保存
- Kubernetes 资源批量删除
- WebSocket 频道订阅管理
- 插件消息转发
- SSH 真正连通性测试
- SSH 真实服务器指标采集

## 五、建议

1. 对所有尚未闭环但已暴露到 UI 的动作增加能力门禁，至少改为 disabled、实验中标签或明确提示未实现。
2. 将“连接测试返回固定成功”与“模拟保存”类假实现列为首批整改项，这些问题会直接误导用户决策。
3. 为插件消息、订阅管理和资源批量操作分别补齐最小可用链路，不要继续让 UI 先于行为完成。
