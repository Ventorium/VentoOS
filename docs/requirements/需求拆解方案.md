# VentoOS 未完成需求拆解与实施方案

> 创建日期：2026-03-31

## 总览

根据需求完成状态核查，共有 ~20 项未完成需求。按影响面和依赖关系拆解为 4 个优先级批次、11 个工作包。

---

## Phase 1: 核心功能补全（高优先级，后端独立 crate）

### WP-1: K8s 真实 API 集成

**现状**: ventoos-k8s 仅解析 kubeconfig YAML，所有 API 返回 stub/硬编码
**目标**: 通过原生 HTTPS 调用 K8s API，实现真实的集群连接、命名空间列表、资源列表

**子任务**:
| # | 子任务 | 方案 |
|---|--------|------|
| 1.1 | K8s HTTP 客户端 | 解析 kubeconfig 获取 server URL / CA / token，使用 rustls + hyper 或 tokio TcpStream + native-tls 发 HTTPS 请求 |
| 1.2 | 集群连接测试 | GET /api 或 /version 验证连通性和认证 |
| 1.3 | 列出命名空间 | GET /api/v1/namespaces，解析 JSON |
| 1.4 | 列出资源（按类型） | GET /api/v1/namespaces/{ns}/pods 等，通用函数按 GVR 构造 URL |
| 1.5 | 资源详情 | GET 单个资源，返回完整 JSON |
| 1.6 | 补充测试 | mock HTTP 响应测试解析逻辑 |

**依赖**: 需在 workspace Cargo.toml 添加 rustls / hyper 或使用更轻量的方案（直接 tokio+rustls 手写 HTTP）
**替代方案**: 鉴于项目原则"减少第三方库"，可用 tokio::net::TcpStream + rustls 包装，手写最小 HTTP/1.1 GET 请求，避免引入完整 hyper/reqwest

---

### WP-2: Database PG/MySQL 真实连接

**现状**: ventoos-db 仅 SQLite（rusqlite）完整，PG/MySQL 仅 TCP 连接测试
**目标**: 支持 PG/MySQL 的 schema 浏览、表结构、数据查询

**子任务**:
| # | 子任务 | 方案 |
|---|--------|------|
| 2.1 | PostgreSQL 协议客户端 | 添加 tokio-postgres（轻量）或手写 PG wire protocol 基础实现（StartupMessage→AUTH→Query→DataRow） |
| 2.2 | MySQL 协议客户端 | 添加 mysql_async 或手写 MySQL 协议基础（Handshake→Auth→COM_QUERY） |
| 2.3 | PG schema 浏览 | `SELECT schema_name FROM information_schema.schemata` |
| 2.4 | PG 表结构 | `SELECT column_name, data_type... FROM information_schema.columns WHERE table_schema=$1 AND table_name=$2` |
| 2.5 | PG 表数据分页 | `SELECT * FROM {schema}.{table} LIMIT $1 OFFSET $2`（参数化防注入） |
| 2.6 | PG SQL 执行 | 执行任意 SQL 并返回结果集 |
| 2.7 | MySQL 同上流程 | schema/表结构/数据查询 |
| 2.8 | 连接池管理 | 简单的 HashMap<Id, Connection> 池 |
| 2.9 | 补充测试 | 使用 mock 或内存 SQLite 测试查询转换逻辑 |

**依赖**: 需添加 tokio-postgres + mysql_async 到 workspace
**注**: 手写 PG/MySQL 协议工作量巨大且容易出错，建议用成熟依赖

---

### WP-3: Redis 改进

**现状**: 手动 RESP2 协议，基本可用但无 Pub/Sub
**目标**: 提升稳定性，可选升级 RESP3，补充 Pub/Sub 基础

**子任务**:
| # | 子任务 | 方案 |
|---|--------|------|
| 3.1 | 完善 RESP 解析器 | 修复 edge cases（大 bulk string、nested array），添加 RESP3 map/set/null 类型解析 |
| 3.2 | 连接 AUTH 增强 | 支持 ACL AUTH（username + password），支持 SELECT db |
| 3.3 | Pub/Sub 基础 | 实现 SUBSCRIBE/PSUBSCRIBE/UNSUBSCRIBE，独立连接用于订阅 |
| 3.4 | MONITOR 命令 | 独立连接发 MONITOR，通过 WS 推送到前端 |
| 3.5 | 补充测试 | RESP 解析器单元测试、命令构造测试 |

**依赖**: 无新依赖，在现有 tokio TcpStream 基础上增强

## 执行策略

### 并行批次

```
Batch 1 (可并行，独立 crate):
  ├── Sub-Agent A: WP-1 K8s 真实 API
  ├── Sub-Agent B: WP-2 Database PG/MySQL
  └── Sub-Agent C: WP-3 Redis 改进

Batch 2 (可并行，前端独立):
  ├── Sub-Agent D: WP-5 虚拟滚动
  ├── Sub-Agent E: WP-6 Explorer 拖拽
  └── Sub-Agent F: WP-7 SSH Agent 清理

Batch 3 (顺序，有依赖):
  └── Sub-Agent G: WP-4 后端架构重构

Batch 4 (顺序，依赖 HTTPS 能力):
  └── Sub-Agent H: WP-8 AI 集成

Batch 5 (最后):
  ├── Sub-Agent I: WP-9 VFS SFTP
  └── Sub-Agent J: WP-10 前端测试
```

### 约束
- 每个 Sub-Agent 只修改自己范围内的文件
- 修改 workspace Cargo.toml 的操作需协调，不并行
- 所有变更必须通过 cargo test / pnpm build
