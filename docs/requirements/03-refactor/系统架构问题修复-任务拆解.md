## 原始需求概述

对当前系统中存在的 9 个架构/功能问题进行全面修复，涵盖菜单注册系统、K8s namespace切换、AI设置、Terminal应用、SSH连接、数据库模块等。

## 问题分析与方案

### 1. 应用菜单（App Menu）与 Tray 注册系统

**现状问题**：
- 应用没有统一的菜单注册机制，Explorer 等应用自行在组件内实现菜单逻辑
- TopBar 的应用菜单仅提供"关于"、"隐藏"、"新建窗口"、"退出"等通用项
- 无法像原生OS那样让应用自定义菜单栏（如 File/Edit/View 等）
- 没有 Tray（通知区域图标）概念

**设计方案**：

#### 1.1 AppMenu 类型系统

在 `AppManifest` 中新增可选的 `menus` 和 `tray` 字段：

```typescript
// web/src/kernel/apps/menu.ts

export interface AppMenuItem {
  id: string
  label: string
  icon?: React.ReactNode
  shortcut?: string          // e.g. '⌘N', '⌘,', 'Ctrl+S'
  disabled?: boolean
  hidden?: boolean
  danger?: boolean
  action?: () => void
  children?: AppMenuItem[]   // 子菜单
}

export interface AppMenuGroup {
  id: string                 // e.g. 'file', 'edit', 'view'
  label: string              // e.g. '文件', '编辑', '视图'
  items: AppMenuItem[]
}

export interface AppTrayConfig {
  icon?: React.ReactNode     // Tray图标，默认使用app icon
  tooltip?: string
  onClick?: () => void
  menuItems?: AppMenuItem[]  // 右键/点击展开的菜单
}
```

#### 1.2 菜单注册 Store

新建 `web/src/kernel/apps/menu-store.ts`，管理运行时菜单状态：
- 应用通过 `registerAppMenus(appId, menus)` 注册菜单
- 应用通过 `registerAppTray(appId, tray)` 注册 Tray
- TopBar 根据当前焦点应用渲染对应菜单
- Tray 区域渲染所有已注册的 Tray 图标

#### 1.3 Hooks

- `useAppMenus(appId)`: 获取指定应用的菜单
- `useActiveAppMenus()`: 获取当前焦点应用的菜单
- `useAppTray(appId)`: 获取应用的 Tray 配置
- `useAllTrays()`: 获取所有 Tray 图标

#### 1.4 TopBar 改造

- TopBar 左侧：Logo → 应用名 → **应用菜单组**（File/Edit/View等）
- TopBar 右侧：**Tray 区域** → 通知 → 主题 → 时钟

#### 1.5 AppManifest 扩展

在 manifest 中可声明静态菜单，同时支持运行时动态更新。

### 3. K8s Namespace 全局切换 + 文件路径修复

**现状问题**：
- K8s 默认使用 `default` namespace，切换 namespace 的 UI 位置不够醒目
- 从本机选择 kubeconfig 文件时，因 VFS 默认挂载 `~/ ` 导致路径缺少前缀

**修复方案**：

#### 3.1 文件路径问题（从 FilePicker 层面解决）
- `VfsPathPickerInput` 返回的 path 是相对于挂载点根目录的相对路径
- 当 mount kind 为 `local` 且 root 为 `~` 时，返回的路径前需要拼接 mount root
- 在 `VfsPathPickerInput` 的 `onSelect` 中，自动将 mount root 与相对路径拼接为绝对路径
- 这是一个通用修复，所有消费 FilePicker 的应用都会受益

#### 3.2 Namespace 切换
- 在集群连接后的顶部工具栏区域添加 namespace 下拉选择器
- 切换 namespace 后刷新当前资源列表

### 4. AI 助理设置

**现状分析**：
- AI 助理已有完整的 4-tab 配置面板（Providers、Agents、Runtime、Channels）
- 用户认为"没有任何设置的地方"可能是因为设置入口不够明显

- 点击后跳转/打开 AI 助手应用的设置面板
- 或者在系统设置中嵌入 AI 核心配置（Provider、默认模型等），详细配置仍在 AI 应用内

### 5. Terminal 应用

**现状**：
- SSH 应用中已有 WebShell 功能（基于 xterm.js）
- 但没有独立的 Terminal 应用入口
- Shell 配置加载需要考虑 macOS 的 `.zshrc`

**设计方案**：

#### 5.1 独立 Terminal 应用
- 注册为新应用 `terminal`，支持 multiWindow
- 基于 xterm.js + WebSocket（复用现有的 `/ws/shell` 端点）
- 多标签支持：每个标签一个独立的 WebSocket 连接

#### 5.2 Shell 配置
- 后端已使用 `$SHELL` 环境变量自动检测 shell（macOS 上通常是 zsh）
- 设置 `TERM=xterm-256color` 已在后端实现
- zsh 会自动加载 `~/.zshrc`（因为是通过 login shell 启动）
- 确保 PTY 的 `CommandBuilder` 使用 `-l` 参数启动 login shell

#### 5.3 功能特性
- 多标签管理（新建、关闭、切换标签）
- 标签重命名
- 分屏（水平/垂直）— 可作为后续增强
- 字体大小调节
- 搜索功能
- 主题跟随系统

### 6. SSH 模块连接修复

**现状**：
- `handle_ssh_shell()` 为 stub，只返回 "SSH connection not yet implemented"
- 项目已有 `russh` 依赖

**修复方案**：
- 使用 `russh` 实现 SSH 连接：读取服务器配置 → 建立 SSH session → 打开 channel → 绑定到 WebSocket
- 支持密码认证和密钥认证
- SSH Shell 在前端复用 Terminal 组件，不作为独立窗口

### 9. 数据库序列化 Bug + 字段对齐

**Bug 分析**：
- Rust 端 `DbEngine` 使用 `#[serde(rename_all = "snake_case")]`
- `PostgreSql` 序列化为 `postgre_sql`（非 `postgresql`）
- `MySql` 序列化为 `my_sql`（非 `mysql`）
- 前端发送 `postgresql` / `mysql`，后端反序列化失败

- 另外，前端使用 `sqlite_path` 字段名，后端使用 `file_path`

**修复方案**（两边对齐）：

#### 方案A（推荐）—— 后端使用 `#[serde(rename)]` 单独标注
```rust
pub enum DbEngine {
    #[serde(rename = "postgresql")]
    PostgreSql,
    #[serde(rename = "mysql")]
    MySql,
    #[serde(rename = "sqlite")]
    Sqlite,
}
```

#### 字段名对齐
将后端的 `file_path` 改为 `sqlite_path`，或前端对齐到 `file_path`。
推荐**统一为 `file_path`**（因为语义上是文件路径，且后端已用此名）。
