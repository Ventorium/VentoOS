# VentoOS - AI & Agent 设计

## 1. AI 定位

AI 是 VentoOS 的系统级操作入口、任务规划层和自动化执行器，而不是一个孤立聊天页。

AI 的职责不是替代每个专业应用，而是把系统能力、当前上下文和用户目标连接起来，完成：

* 查询型操作。
* 导航型操作。
* 批量型操作。
* 分析型操作。
* 自动化执行型操作。

## 2. 第一阶段 Agent 策略

第一阶段不自研完整 Agent 引擎，而是优先接入用户本机已成熟的 Agent 工具：

* Claude Code
* Codex
* OpenCode

VentoOS 负责的不是“训练大模型”，而是提供：

* Agent Engine Adapter
* Tool / Skill 注册体系
* 上下文注入
* 权限确认
* 任务编排
* 结果回写

这样做的原因：

* 最快落地。
* 复用已有高质量模型交互体验和执行能力。
* 把研发投入聚焦在系统能力封装与操作闭环上。

## 3. 核心能力模型

标准执行链路：

用户输入 ->
意图解析 ->
上下文构建 ->
任务规划 ->
Tool 选择 ->
权限审查 ->
执行 ->
结果整合 ->
结果反馈与审计

上下文来源至少包括：

* 当前激活窗口。
* 当前应用。
* 当前选中的资源。
* 当前连接或集群上下文。
* 最近任务与失败记录。
* 用户显式提供的输入内容。

## 4. Agent 系统分层

### 4.1 Input Layer

输入方式：

* 文本输入。
* 语音转文字。
* 命令面板快捷指令。
* 从应用内部“Ask AI”入口带上下文调用。

### 4.2 Understanding Layer

职责：

* 分析意图。
* 判断是否需要调用 Tool。
* 判断是否需要追问或确认。
* 拆分多步骤任务。

这层可以由外部 Agent 引擎承担，但需要 VentoOS 提供结构化上下文。

### 4.3 Planning Layer

职责：

* 把自然语言目标映射为任务计划。
* 选择合适的系统能力。
* 将大任务拆分为子任务。
* 决定哪些步骤需要用户确认。

### 4.4 Tool Runtime Layer

职责：

* Tool 注册与发现。
* 参数校验。
* 风险分级。
* 权限边界控制。
* Tool 调用超时、取消、重试。

### 4.5 Execution Layer

* 由 Rust Core 真正执行所有系统级能力。
* Tool 只负责描述动作，不直接承载底层协议细节。

## 5. Tool 设计原则

所有可被 AI 调用的系统能力必须注册为 Tool。

Tool 必须具备：

* 唯一名称。
* 明确输入输出结构。
* 风险等级。
* 所需上下文。
* 执行超时与取消策略。
* 审计字段。

示例：

* `teleport.login`
* `k8s.cluster.list`
* `k8s.resource.describe`
* `k8s.pod.exec`
* `k8s.port_forward.create`
* `db.connection.test`
* `db.query.run`
* `redis.key.scan`
* `redis.key.delete`
* `vfs.mount.create`
* `vfs.file.copy`
* `system.window.open_app`
* `system.task.list`

## 6. Skill 设计原则

Tool 是原子能力，Skill 是更高层的可复用工作流模板。

例如：

* “排查 Pod 启动失败” Skill：串联事件、日志、资源详情、节点状态。
* “从 K8s 服务打开数据库” Skill：识别服务、创建端口代理、注入临时连接、打开 DB 应用。
* “备份并导出 Redis Key” Skill：搜索 Key、导出文件、保存到 VFS 挂载点。

第一阶段的 Skill 不需要做成复杂开放市场，但内部必须具备注册与执行机制。

## 7. Agent Engine Adapter 设计

适配器最少需要屏蔽以下差异：

* 启动方式：CLI、守护进程、本地 API。
* 会话管理：单轮、长会话、流式会话。
* Tool 调用协议：函数调用、文本协议、MCP 或自定义桥接。
* 输出模式：流式文本、结构化消息、计划步骤、错误信息。

适配器统一对外暴露：

* `start_session`
* `send_message`
* `cancel_session`
* `register_tools`
* `stream_events`
* `close_session`

## 8. 本地 Agent 驱动方案

### 8.1 推荐方案

VentoOS 作为主控层，外部 Agent 引擎作为推理与协作执行层。

职责划分：

* VentoOS：系统能力定义、上下文、权限、审计、任务。
* Agent Engine：理解用户意图、生成计划、决定调用哪些 Tool。

### 8.2 不推荐的第一阶段方案

第一阶段不建议自研完整 Agent Runtime，原因是：

* 成本高。
* 容易陷入模型和工作流基础设施重复建设。
* 与产品核心差异点相比优先级不高。

## 9. 安全策略

* 高风险操作必须确认。
* 所有 Tool 调用可审计。
* AI 无法绕过 Tool Registry。
* AI 不直接持有底层凭据明文。
* 长时间任务必须绑定可取消任务 ID。

高风险操作示例：

* 删除 K8s 资源。
* 对节点执行 `drain`。
* 删除数据库或表。
* 批量删除 Redis Key。
* 删除或覆盖文件。

## 10. 结果呈现

AI 输出不应只有文本，还要能触发系统 UI：

* 打开对应应用窗口。
* 高亮对应资源。
* 附带任务进度。
* 展示执行摘要与详细日志入口。
* 对失败步骤给出下一步建议。

## 11. 语音输入

第一阶段语音输入采用“语音转文字 -> 标准文本链路”的方式。

要求：

* 支持中文与英文。
* 支持手动确认识别结果后发送。
* 支持上下文命令，例如“帮我看看这个 Pod 为什么重启”。

## 12. 未来扩展

* 自动化任务与 Workflow。
* 多 Agent 协作。
* 知识库与操作记忆。
* 基于历史操作生成建议和快捷动作。
