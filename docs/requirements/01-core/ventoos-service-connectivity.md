# VentoOS - 服务直连与跨模块联动设计

## 1. 目标

本设计用于解决一个关键体验问题：用户已经在 Kubernetes 中看到了某个数据库或 Redis 服务，但不应该再被迫手动执行登录、查端口、做 `port-forward`、填写连接信息、打开客户端这一长串步骤。

VentoOS 的目标是把这些步骤折叠为一次上下文感知的“打开资源”动作。

## 2. 适用场景

* 从 K8s Service 直接打开数据库。
* 从 K8s Pod 或 StatefulSet 直接打开数据库。
* 从 K8s Service 直接打开 Redis。
* 从 Ingress / Host 信息推断服务入口后打开对应资源。
* 从 AI 询问“打开这个服务的数据库”后自动完成链路。

## 3. 系统设计原则

* 用户触发的是“打开目标资源”，不是“自己搭链路”。
* 系统负责选择最合适的连接方式。
* 生成的连接默认是临时连接。
* 临时连接可提升为持久连接。
* 所有中间链路都必须是可观测、可取消、可回收的任务。

## 4. 资源识别模型

系统需要具备资源识别器，用于判断一个 K8s 对象是否代表数据库或 Redis 服务。

识别依据至少包括：

* Service 端口，例如 5432、3306、6379、26379。
* Service 名称，例如 `postgres`, `mysql`, `redis`, `master`, `primary`。
* Pod / StatefulSet 容器镜像名。
* 标签与注解。
* 环境变量，例如 `DATABASE_URL`, `REDIS_URL`, `POSTGRES_DB`, `MYSQL_DATABASE`。
* Helm Chart 常见命名模式。

输出结果应包括：

* 猜测类型：PostgreSQL / MySQL / Redis。
* 推荐连接方式。
* 推荐主机、端口、数据库名、用户名候选。
* 置信度。

## 5. 连接建立策略

### 5.1 直接可达

如果目标 Service / Ingress 已可从本机直接访问：

* 直接创建临时连接。
* 打开目标应用。

### 5.2 需要 K8s 代理

如果目标资源只在集群内可见：

* 自动创建 Port Forward 或等价代理。
* 将本地临时端口与目标应用连接配置绑定。
* 代理关闭时临时连接自动失效。

### 5.3 需要多跳隧道

如果目标资源需要同时依赖 Teleport、K8s、SSH 或 HTTP 隧道：

* 由 Rust Core 负责编排多跳链路。
* 对用户展示为单个“连接建立中”任务。

## 6. 临时连接模型

临时连接至少包含：

* 来源资源 ID
* 来源集群 / 命名空间
* 目标类型
* 链路方式
* 本地代理端口
* 生命周期
* 是否可保存

临时连接行为：

* 默认只在当前会话或窗口内有效。
* 用户可一键另存为常驻连接。
* 链路失效时自动提示重新建立。

## 7. 用户交互设计

### 7.1 入口位置

至少需要以下入口：

* K8s 资源列表右键菜单。
* K8s 资源详情页快捷按钮。
* Port Forward 面板中的“作为数据库打开 / 作为 Redis 打开”。
* AI 对话结果中的行动按钮。

### 7.2 交互流

推荐流程：

1. 用户点击“打开数据库”或“打开 Redis”。
2. 系统识别资源并展示建议配置。
3. 如无需确认，直接进入后台建立链路。
4. 若需要补充用户名、密码、数据库名，则弹出轻量面板补全。
5. 建立成功后自动打开对应应用窗口。
6. 窗口顶部展示“临时连接”标记及链路来源。

## 8. 跨模块状态同步

建立直连后，系统需要同步以下状态：

* 任务中心记录连接建立任务。
* 通知中心显示成功或失败。
* Database / Redis App 收到连接上下文并打开窗口。
* K8s App 能看到该资源已有活跃关联连接。

## 9. AI 场景

AI 可以触发这类联动，例如：

* “打开这个 Service 对应的 Redis。”
* “帮我连上这个 Postgres 看看有哪些表。”
* “为这个 MySQL 建一个临时连接，不要保存。”

AI 执行时：

* 必须使用资源识别器和连接建立策略。
* 如需要密码或高风险操作，仍然要求用户确认。

## 10. 风险与边界

* 资源识别可能误判，因此要显示置信度与可编辑候选配置。
* 自动链路建立失败时要暴露真实错误，而不是只提示“连接失败”。
* 临时代理必须自动清理，避免端口泄漏和僵尸进程。
